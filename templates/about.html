How it works, what runs where, and how to get the best performance.

How it works

JavaLab runs real Java, entirely inside your browser. There is no server-side JVM — the site only hands out static files; everything executes in your own tab.

  • Engine — CheerpJ by Leaning Technologies: a full Java virtual machine compiled to WebAssembly. When you open an app, your browser downloads the CheerpJ runtime plus the app's .jar and interprets / JIT-compiles the Java bytecode in a WebAssembly sandbox.
  • Java version — Java 8. It's pinned there because Swing, threads, and javax.sound.sampled audio all work reliably under CheerpJ on the Java-8 runtime.
  • Display & input — each app paints into an HTML <canvas>; your mouse, keyboard, and (on phones) on-screen touch controls are forwarded to the Java app.
  • Isolation — every app runs in its own iframe "realm". Closing it tears down the whole runtime — threads, audio lines, static singletons — so apps never bleed into each other.
What this means for you
  • Your stuff stays yours. Jars you upload and code you write live in your browser (IndexedDB) and are never sent to a server.
  • No execution server. Nothing you run executes remotely — there's no server-side attack surface, just WebAssembly in your tab.
  • Performance is virtualized. Because the JVM itself runs as WebAssembly, apps are slower than on a native JVM. That overhead comes from the emulation layer, not the app — which is why heavier games show a one-time performance notice.
  • Networking goes through a relay. Browser sandboxes can't open raw TCP sockets, so the networked apps (Seas of Yore online play, Site Selector) tunnel through a small WebSocket relay/proxy instead.
Compatible browsers

Any modern browser with WebAssembly and canvas support works — on desktop and mobile:

  • Chrome / Chromium / Edge / Brave — usually the smoothest WASM performance.
  • Firefox — fully supported.
  • Safari (macOS / iOS) — supported.

Keyboard-driven games (e.g. Javarominoes) show an on-screen gamepad on phones and tablets.

Get the best performance

CheerpJ is CPU-heavy (a JVM running as WebAssembly) and leans on the GPU for canvas rendering, so the single biggest win is hardware acceleration. Keep your browser up to date, close heavy background tabs, and prefer a Chromium-based browser if you can.

Firefox

  • Settings → General → Performance: untick "Use recommended performance settings", then make sure "Use hardware acceleration when available" is on.
  • For finer control, open about:config and set:
    • gfx.webrender.all → true  (GPU compositing/rendering)
    • media.ffmpeg.vaapi.enabled → true  (Linux: hardware video decode)
  • Verify at about:support — under Graphics, "Compositing" should read WebRender.

Chromium-based (Chrome, Brave, Edge, …)

  • Settings → System: ensure "Use graphics acceleration when available" is on, then restart the browser.
  • Check chrome://gpu — the items at the top (Canvas, Compositing, WebGL, Rasterization) should say "Hardware accelerated".
  • On Linux, if the GPU is blocklisted, launch with flags to force acceleration (one command):
google-chrome-stable \
  --ignore-gpu-blocklist \
  --enable-gpu-rasterization \
  --enable-zero-copy \
  --use-gl=angle --use-angle=gl \
  --enable-features=VaapiVideoDecoder \
  --enable-accelerated-video-decode \
  --disable-features=UseChromeOSDirectVideoDecoder

For CheerpJ the rasterization/compositing flags matter most (canvas rendering); the Vaapi/video flags mainly help HTML5 video. These are advanced, mostly-Linux tweaks — on most machines hardware acceleration is already on by default. --use-gl=desktop works on some setups in place of the ANGLE flags.

Safari & mobile

  • Safari accelerates automatically — just keep iOS/macOS current.
  • On phones/tablets, plug in or disable low-power/battery-saver mode so the CPU isn't throttled, and use the Maximize button for a full-screen play area.
